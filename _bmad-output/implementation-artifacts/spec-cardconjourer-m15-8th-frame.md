## Intent

**Problem:** Cardconjourer's frame flags (`--8th`/`--modern`/`--retro`/`--borderless`) don't expose Card Conjurer's already-vendored `'M15Eighth'` hybrid frame (modern M15 body + 8th Edition styling), even though the engine ships full support for it (crowns, PT box, DFC packs) with no new assets needed.

**Approach:** Add a fifth mutually-exclusive frame flag, `--m15-8th` (CLI + `#cardconjourer` modeline), that maps to CC's `'M15Eighth'` frame type — mirroring `--modern`'s single-face and DFC wiring but substituting the `packM15Eighth*.js` pack family. Never auto-selected (no Scryfall `frame` value corresponds to it).

## Boundaries & Constraints

**Always:**
- `--m15-8th` joins the existing `frame_group` argparse mutex (cli.py) alongside `--8th`/`--modern`/`--retro`/`--borderless`, and the matching `#cardconjourer` modeline mutex (modelines.py).
- Supports single-faced AND transform/modal_dfc cards via the existing `packM15Eighth.js`, `packM15EighthTransformFront.js`, `packM15EighthTransformBack.js`, `packM15EighthModal.js` pack files — no new CC assets.
- Legend crowns use the engine-native `makeM15EighthFrameByLetter` builder (already registered in `autoFrame.js`, `supportsCrown: true`) — no custom harness crown code.
- Follows `'modern'`'s M15 geometry for bottom-info layout and the rules-height fix, since M15Eighth shares M15's bounds.
- `autoFrameUnified`/`frameTypeLiteral` target is `'M15Eighth'`.

**Ask First:** none anticipated — engine support is already confirmed present in the vendored cache. If `packM15Eighth*.js` are missing from a given user's `cc_cache` checkout at runtime, HALT and ask rather than silently falling back to another frame.

**Never:**
- No new Card Conjurer pack/asset files — engine-native only.
- Do not restructure the existing `'8th'`/`'retro'`/`'borderless'` branches — only add sibling `'m15-8th'` branches.
- Do not add `'m15-8th'` to `SCRYFALL_FRAME_TO_STYLE` — it must never be auto-selected.

## Spec Change Log

- **2026-07-23, during implementation (not a step-04 loopback):** Manual visual QA (user inspection of a rendered card) found the first implementation routed `m15-8th` through modern's full bottom-info layout (`setBottomInfoStyle()` — multi-part set/rarity/artist/copyright). User feedback: it should use 8th's compact single-line bottom-info style instead, repositioned to sit on modern's (thinner) border geometry. Fixed in `harness.js`: `m15-8th` now gets its own branch calling `setLeanBottomInfo()` (8th's template, unchanged) with a Y-offset applied to align with modern's bottom-info band. Verified visually against 8th, modern, a legendary (crown), and a transform DFC front/back — all render correct per-card artist/set/collector-number in the right style and position. KEEP: the artist/collector-number *values* were never wrong in the original implementation (both paths read the same `#info-*` DOM state) — the bug was purely the visual *style/position* of that text, not the data.
- **2026-07-23, continued (not a step-04 loopback):** Further visual QA found `packM15Eighth.js` actually has its own bespoke native `loadBottomInfo()` template (own artist glyph, own "Wizards of the Coast, Inc." wording) — the `setLeanBottomInfo()` approach above was replaced with leaving the pack's native template untouched, only repositioning `wizards` (copyright line): vertically centered against the artist line, right-aligned mirroring the artist icon's left-edge gap — except on creatures/vehicles, where a P/T box leaves too little row width to share a line without collision on long names, so those fall back to the pack's native stacked order (just re-spaced to stop the two lines overlapping). Separately found and fixed a real pre-existing engine limitation: colored artifact creatures (e.g. a black-mana artifact) get both an "Artifact Frame" layer (the actual light-colored visible border — authentic Magic templating) and a "Black Frame" layer (inner rules-box tint), and the engine's `{conditionalcolor:...}` token does a substring match across all active frame layers rather than just the one behind the text, so it wrongly matches "Black Frame" and forces illegible white-on-light text. Fixed by detecting the same condition the engine's own `cardFrameProperties` uses (type line contains "Artifact", not "Vehicle"/"Land") and forcing black. Also confirmed via an isolated `--modern` test that a separate, pre-existing, cross-frame low-contrast bug on MDFC Land back faces is NOT `m15-8th`-specific — logged to `deferred-work.md` rather than fixed here. KEEP: `width` must stay at the pack's original value in all cases — narrowing it to force alignment causes the engine to auto-shrink the font into illegibility.
- **2026-07-24 (not a step-04 loopback):** User found the creature-stacked layout from the prior entry still put the copyright line in the wrong visual position, and requested a scope change: drop the real-card copyright/legal text entirely and replace it with a compact `(SET) NUMBER` tag (e.g. `(WOE) 78`) whose only purpose is identifying the physical card during print staging — this is a proxy, not a real card, so the legal fine print serves no purpose. Implemented via literal `{elemidinfo-set}`/`{elemidinfo-number}` engine tokens (same resolution mechanism the pack's own template used) replacing the old copyright string, keeping the `{conditionalcolor:...}` prefix intact for non-artifact-frame color correctness. Since the new tag is short, it no longer collides with even a long artist name, so the creature/vehicle stacked-fallback layout from the prior entry was removed — the shared-row right-aligned layout is now used unconditionally (still capped before the P/T box on creatures/vehicles). Verified visually on a legendary creature, a colored artifact creature, and a no-P/T-box card. CLAUDE.md's `--m15-8th` description updated to document the tag replacing copyright text. KEEP: the artifact-frame black-text-forcing fix and the `{elemidinfo-set}`/`{elemidinfo-number}` token substitution both still apply and must survive future edits to this block.
- **2026-07-24 (not a step-04 loopback):** User reported gold multicolor cards were still poorly readable and mono-black cards were sometimes obscured. Empirical trace (temporary debug instrumentation on the vendored engine, reverted after) found gold multicolor cards that include black in their color identity (e.g. a BR legendary) get a "Black Frame" pinline layer in addition to the actual visible "Multicolored Frame" border — the same class of layer-vs-background mismatch as the artifact case, just via the pinline. A UW or RG gold card never hits this; only combinations including black do. Fixed by extending the black-text-forcing check to also cover multicolor (mirroring `cardFrameProperties`' own frame-letter resolution: 3+ colors, or 2 non-hybrid colors, both resolve to 'M' regardless of which colors). Separately, mono-black cards showing white text are *correct* (the border genuinely is black) but the M15Eighth black frame art has embossed highlight texture that locally breaks contrast — fixed by adding a black outline (`outlineWidth: 0.003`) to both bottom-info lines unconditionally; a same-color outline on already-black text (all other colors) is a visual no-op, so no separate conditional was needed. Verified visually on a BR legendary, a mono-black instant, and re-verified all four prior cases (artifact, no-P/T-box, legendary, and the P/T-box stacking case) still hold. **Correction in the next entry: the "same-color outline is a visual no-op" assumption here was wrong** — see below.
- **2026-07-24, continued (not a step-04 loopback):** User reported the multicolor fix produced "black font with black outline" on Alesha — the prior entry's assumption was wrong: a same-color outline at this font's small size thickens the small-caps glyphs into a bold, blobby mess (confirmed via a zoomed crop of the rendered PNG), not a harmless no-op. Fixed by scoping the outline to only the cases actually expected to resolve white — Land, Vehicle, or mono-black not already forced black by the artifact/multicolor case — mirroring `cardFrameProperties`' frame resolution precisely instead of applying unconditionally. Separately, user reported the `(SET)` part of the new tag rendered in italics. Root cause: the vendored engine italicizes any parenthesized text in a text object carrying a `.name` property (creator-23.js, gated on our own `#italicize-reminder-text: true` setting needed for genuine rules-text reminder text), exempting only Title/Type/Mana Cost/Power-Toughness. The pack's native `wizards` field carries `name:'wizards'`; `top` (artist line) was never named, which is why it was never affected. Fixed by deleting `wizards.name` after the text swap — nothing else in this per-card render path reads it (the only other consumer is a URL-param copyright override for the interactive GUI). Verified visually: Alesha's text is now thin/crisp with no outline and both the artist name and `(SET) NUMBER` are upright; Murder (mono-black) still shows the outlined white text correctly. KEEP: outline scoping must stay precise (Land/Vehicle/mono-black-non-forced only) — do not revert to "apply everywhere". `wizards.name` must stay deleted — do not reintroduce a `.name` on that field.
- **2026-07-27 (not a step-04 loopback; new feature, not an m15-8th fix):** User found Station (Edge of Eternities) cards render as generic Artifact cards under any frame, including m15-8th — Card Conjurer has no Station entry in `autoFrame.js`'s frame-type registry at all, but does have real, complete, unused assets: `packStationRegular.js`/`packStationBorderless.js` plus a 42KB `versionStation.js` init script (tiered ability badges, tinted ability backgrounds, a dedicated Station P/T badge) built for the interactive GUI. Agreed a 5-phase plan with the user (routing → ability text → badges/squares → Station P/T → bottom-info); this entry covers phase 1 (routing) only, explicitly scoped to "no funny stuff" — no ability parsing, no badge/square/PT wiring yet. Added `isStationCard()` (keyword check) and override `frame = 'station'` in `renderCard`, unconditionally, regardless of the requested `--frame` — real Station printings are always modern-era, there's no "Station styled as 8th" to render. Added a `'station'` case to `packForLayout` and a bypass in the `autoFrameUnified` call chain (Station's own pack onclick already builds its layers via `initializeStationFrame`; calling `autoFrameUnified` too would build a second, conflicting layer set). Found and fixed two bugs surfaced by this, both real and independent of Station: (1) `versionStation.js`'s own `updateImageFromMana` crashed on `undefined.endsWith` — traced to our own `document.querySelector` shim in `harness.js`, which fabricates a truthy fake element for *any* selector string including attribute-selector cache-lookups like `img[data-station-cache="…"]`, so `setupStationImage`'s "does a cached image already exist" check always returned true and never created the real `Image()` object; fixed by returning `null` for any selector containing `[`/`]` (verified this exact selector pattern is used nowhere else in any engine/pack file we load, so the fix is safely scoped). (2) Station's own onclick never calls `addFrameByName` for its per-color frame art (unlike every other pack) since it isn't wired into `autoFrameUnified` at all — without an explicit call the card rendered as bare full-bleed art with no border/pinline/title-bar graphic; fixed by adding one `addFrameByName([getFrameNameForFace(face), 'Artifact Frame'])` call in the new 'station' branch (Station's pack has no plain "Colorless Frame", only per-color + Land + Eldrazi, hence the Artifact fallback). Verified visually on a green artifact-creature Station and a land Station, and confirmed override fires even when `--8th` is explicitly requested. **Correction, see next entry:** the "12+" seen on a land Station in this pass was misdiagnosed as automatic tier-number detection — it wasn't; see below. KEEP: `querySelector`'s bracket-selector → `null` fix and the `addFrameByName` frame-art call are both load-bearing for this phase; do not remove either while iterating on later phases.
- **2026-07-27, continued (still routing-adjacent, not ability parsing):** User reported the bottom-info fix above was correct but flagged three more things still off: (1) legendary Stations get no crown — added `frame === 'station'` to the crown-builder chain alongside 'modern' (same modern-fallback reasoning as bottom-info), but it produced no visible crown; not investigated further (Station's full-bleed art layout likely leaves no room where M15 expects one) and left in as a no-op pending a real look in a later phase. (2) The round tier badge has no circle/background. (3) The P/T box has no background/border either — user asked "are you sure you're loading the frame correctly?" pointing out these work automatically on the real Card Conjurer website. Root cause for (3), and it turned out to double as the reason (2) looked broken too: our own `HarnessImage` class (harness.js's replacement for the browser's native `Image`, used by every vendored script including `versionStation.js`) never implements `.complete`/`.naturalWidth`/`.naturalHeight` — real browsers maintain these automatically, so `drawStationElement`'s `if (image?.complete && image.naturalWidth > 0)` guard always saw `undefined` and silently skipped drawing the image, regardless of whether it had actually loaded. Fixed by adding those three as getters backed by `_inner` (the loaded node-canvas image). Separately, even with that fixed, the very first automatic `stationEdited()` call (triggered by `versionStation.js`'s `textEdited` override during `importCard`) fires before the async image load resolves, so a redraw is needed afterward — added `if (frame === 'station') global.stationEdited();` right after the existing pending-images drain loop (the same drain point `renderBottomInfo`'s set-symbol de-overlap logic already relies on for the same reason). Verified: the P/T box now renders with its proper black bordered background on both a legendary and a non-legendary Station. The round badge *circle* still doesn't appear — traced this to `card.station.badgeValues` being genuinely empty (`["","",""]"`) even after the fix, confirmed by temporary debug instrumentation (removed after use) showing the badge image itself loads correctly (`complete=true`, correct per-color asset) but `hasValue()` gates on a non-empty numeric badge value that nothing has ever set. The "12+" seen earlier on the land Station was not auto-detected tier data — it was literal unparsed oracle_text leaking through, consistent with ability-text parsing genuinely not being implemented yet. So: frame art, bottom-info, and P/T background are now correct and complete; the badge number itself needs real phase-2/3 work (parsing oracle_text tiers into `card.station.badgeValues`), it was never "automatic." KEEP: the `.complete`/`.naturalWidth`/`.naturalHeight` getters on `HarnessImage` and the post-drain `stationEdited()` re-call are both load-bearing and apply to any future pack that checks image-load state before drawing, not just Station.
